Claude Code や Codex CLI のような AI エージェントにサーバー設定を任せていると、「API キーを `.env` に追加してください」と言われる場面が来ます。ここで値をチャットに貼ったり、エージェントにコマンドごと実行させたりするのは絶対に NG。秘密が会話ログに平文で残ってしまいます。

防ぎ方はシンプルで、**シークレットを標準入力で渡す**ことです。`read -s` で値を画面に出さずに受け取り（非エコー入力、サイレント入力とも呼ばれます）、コマンドの引数には載せずに書き込み先へ流します。ターミナルで 4 行を順に打つだけです。

## 秘密が残る 3 つの場所

ターミナルで秘密を扱うとき、値が残りうる場所は 3 つあります。

| 場所 | 残る条件 | 見える人 |
|---|---|---|
| シェル履歴（`~/.zsh_history`・`~/.bash_history`） | コマンド文字列に値を直接書いた | そのファイルを読める人・バックアップ |
| プロセス一覧（`ps`） | 外部コマンドの**引数**に値が載った | 実行中は同じマシンのほかのユーザーからも見える（Linux で `hidepid` を設定している場合を除く） |
| AI エージェントの会話ログ | チャットに値を貼った／エージェントが値を含むコマンドを実行した・出力を読んだ | ログファイルを読める人（Claude Code なら `~/.claude/projects/` 配下の JSONL に平文で保存） |

1 つ目と 2 つ目は昔からある話で、3 つ目が AI エージェントを使うようになって増えた経路です。エージェントは「ユーザーの代わりにコマンドを打つ」のが仕事なので、気をつけていないと秘密もそのまま渡してしまいます。

## やってはいけない書き方

先に、やってはいけない NG な書き方を確認しておきます。

```bash
# NG 1: 値を直接書く → シェル履歴に残る
echo 'SLACK_BOT_TOKEN=xoxb-xxxxxxxx' >> ~/apps/my-bot/.env

# NG 2: ssh の引数に変数を展開する → ローカルとリモート両方の ps に値が見える
ssh my-vps "echo SLACK_BOT_TOKEN=$SLACK_TOKEN_INPUT >> ~/apps/my-bot/.env"
```

NG 2 は変数を使っているので安全に見えますが、`$SLACK_TOKEN_INPUT` はダブルクォートの中でローカルのシェルが展開します。展開後の文字列が `ssh` コマンドの引数になり、リモート側でもシェルの引数として実行されます。実行中の数秒間、`ps` を叩けば値がそのまま読めます。

加えて、AI エージェントとの間では次の 2 つも避けます。

- **チャットに値を貼る**：会話ログに残ります。利用しているサービスによってはサーバー側にも残ります
- **エージェントに実行させる**：エージェントが打ったコマンドと出力は、すべて会話ログに記録されます。Claude Code の `! <command>`（ユーザーがセッション内でコマンドを実行する機能）も、コマンドと出力が会話に入るので同じです

:::message
シェルには「先頭にスペースを付けたコマンドを履歴に残さない」設定（bash の `HISTCONTROL=ignorespace`、zsh の `setopt HIST_IGNORE_SPACE`）もあります。ただし、これで防げるのはシェル履歴だけで、`ps` と会話ログには効きません。
:::

## 結論：この 4 行を覚えておけばよい

ローカルの `.env` に Slack の bot token を追記する例です。

```bash
read -rs SLACK_TOKEN_INPUT
printf '\nSLACK_BOT_TOKEN=%s\n' "$SLACK_TOKEN_INPUT" >> ~/apps/my-bot/.env
unset SLACK_TOKEN_INPUT
grep -cE '^SLACK_BOT_TOKEN=.+' ~/apps/my-bot/.env
```

- 1 行目で値を受け取る（画面には出ない）
- 2 行目でファイルに追記する（値はコマンド文字列に書かない）
- 3 行目で変数を消す
- 4 行目で入ったことを値を見ずに確かめる

この形なら、シェル履歴に残るのは `read -rs SLACK_TOKEN_INPUT` という**変数名だけ**です。`ps` にも会話ログにも値は出ません。以下、なぜそうなるのかと、実際の手順を順に説明します。

## なぜ 4 行で漏れないのか

### `read -rs` ─ 画面に出さずに受け取る

`read` は標準入力から 1 行読んで変数に入れるシェルの組み込みコマンドです。2 つのオプションを付けています。

- `-s`：入力した文字を画面に表示しない（パスワード入力と同じ状態）
- `-r`：バックスラッシュ `\` を特別扱いしない。付けないと、値に含まれる `\` が消えます

値はシェルの変数としてメモリに入るだけなので、履歴にもファイルにも書かれません。

### `printf` はシェルの組み込みコマンド

2 行目の `printf` は外部プログラムではなく、bash・zsh とも**シェルの組み込みコマンド**です。

```console
$ type printf
printf is a shell builtin
```

組み込みコマンドは新しいプロセスを起動しないので、引数（ここでは展開後の値）がプロセス一覧に現れません。筆者の Mac（bash 3.2 / zsh 5.9）で、ダミーの値を使って比べた結果が次のとおりです。

| 渡し方                                       | `ps` に値が出たか |
| ----------------------------------------- | ----------- |
| `printf '%s' "$V" \| 別のコマンド`（標準入力で渡す）     | 出ない         |
| `sh -c "... $V ..."`（引数に展開して渡す、NG 2 と同じ形） | 出る          |

### `export` しない、最後に `unset` する

`read` で作った変数は `export` していないので、そのシェルから起動した子プロセスの環境変数にも入りません。用が済んだら 3 行目の `unset` で消し、同じターミナルに値を残さないようにします。

## 手順サンプル 1：ローカルの .env に追記する

ターミナルで 1 行ずつ実行します。**AI エージェントのセッションではなく、自分で開いた別のターミナルで実行してください。**

**1 行目：入力待ちにする**

```bash
read -rs SLACK_TOKEN_INPUT
```

実行するとカーソルが止まって入力待ちになります。ここで token を貼り付けて Enter を押します。`-s` が付いているので画面には何も表示されませんが、値は正しく入っています。止まったように見えても正常です。

**2 行目：.env の末尾に追記する（このまま貼り付けて実行）**

```bash
printf '\nSLACK_BOT_TOKEN=%s\n' "$SLACK_TOKEN_INPUT" >> ~/apps/my-bot/.env
```

`%s` の位置に、1 行目で入れた値が自動で入ります。**token をこのコマンド文字列の中に書き込まないでください。** token を貼るのは 1 行目の入力待ちのときだけです。

**3 行目：変数を消す**

```bash
unset SLACK_TOKEN_INPUT
```

**4 行目：入ったかを確かめる（値は表示されない）**

```bash
grep -cE '^SLACK_BOT_TOKEN=.+' ~/apps/my-bot/.env
```

`1` と出れば成功です。`.+` で「`=` の後ろに 1 文字以上ある」ことまで確かめているので、値が空のまま書き込まれた場合は `0` になります。

実際の画面は次のようになります。1 行目のあとに何も表示されていないのが、値を貼り付けて Enter を押したところです。

```console
$ read -rs SLACK_TOKEN_INPUT
$ printf '\nSLACK_BOT_TOKEN=%s\n' "$SLACK_TOKEN_INPUT" >> ~/apps/my-bot/.env
$ unset SLACK_TOKEN_INPUT
$ grep -cE '^SLACK_BOT_TOKEN=.+' ~/apps/my-bot/.env
1
```

:::message
入力用の変数名（`SLACK_TOKEN_INPUT`）は、ファイルに書くキー名（`SLACK_BOT_TOKEN`）とわざと変えています。「どちらが一時的な入れ物で、どちらが設定の名前か」が区別しやすくなります。
:::

## 手順サンプル 2：SSH でリモートサーバーに入れる

VPS 上のアプリに設定を入れる場合です。ここではバックアップツールが使う、S3 互換ストレージのアクセスキー 2 つを追記します。

```bash
read -rs KEY_ID_INPUT
read -rs SECRET_INPUT
printf '\nAWS_ACCESS_KEY_ID=%s\nAWS_SECRET_ACCESS_KEY=%s\n' "$KEY_ID_INPUT" "$SECRET_INPUT" | ssh my-vps 'cat >> ~/.config/backup/backup.env'
unset KEY_ID_INPUT SECRET_INPUT
```

1・2 行目はそれぞれ入力待ちになるので、1 つずつ貼り付けて Enter を押します。

ポイントは 3 行目です。`ssh` に渡しているコマンドは `cat >> ~/.config/backup/backup.env` だけで、値は含まれていません。値は `printf` からパイプで SSH 接続の標準入力に流れ、リモートの `cat` がそれを受け取ってファイルに追記します。SSH の通信は暗号化されているので、経路上でも読まれません。

- `printf` の書式に `%s` を 2 つ並べ、後ろに変数を同じ順で並べると、複数のキーを一度に書けます
- `ssh` のコマンドをシングルクォートで囲んでいるので、`~` はリモート側で展開されます

確認もリモートで値を出さずに行います。

```bash
ssh my-vps "grep -oE '^[A-Z_]+=' ~/.config/backup/backup.env"
```

```console
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
```

キー名だけが並び、値は表示されません。

:::message
`ssh my-vps` でサーバーにログインしてから、手順 1 の 4 行をそのままサーバー上で打っても安全です。その場合、履歴に残る変数名はサーバー側のシェル履歴に入ります。
:::

## 手順サンプル 3：パスワードファイルを作る

ツールによっては、パスワードを「1 行だけ書いたファイル」で受け取ります（バックアップツール restic の `--password-file` など）。この場合は追記ではなく新規作成で、権限を自分だけに絞ります。

```bash
read -rs BACKUP_PASS_INPUT
printf '%s' "$BACKUP_PASS_INPUT" | ssh my-vps 'umask 077; cat > ~/.config/backup/backup.pass && chmod 600 ~/.config/backup/backup.pass'
unset BACKUP_PASS_INPUT
ssh my-vps 'ls -l ~/.config/backup/backup.pass'
```

- `printf '%s'` は改行を付けずに値だけを書きます
- `>` は上書きです。`>>` と間違えないようにします
- `umask 077` は「これから作るファイルを自分しか読めない権限にする」設定です

`-rw-------` と表示されれば成功です。

:::message alert
`umask` が効くのは**ファイルを新しく作るときだけ**です。すでにファイルがあると、上書きしても元の権限（たとえば誰でも読める `-rw-r--r--`）のまま残ります。上の例で `chmod 600` を続けているのはそのためです。
:::

## 値を見ずに確かめる

秘密を書いたファイルを `cat` やエディタで開くと、せっかく隠した値が画面に出ます。AI エージェントに読ませれば会話ログに残ります。確認は値を出さないコマンドで行います。

| 確かめたいこと | コマンド | 期待する結果 |
|---|---|---|
| キーが 1 つだけあるか | `grep -c '^SLACK_BOT_TOKEN=' ~/apps/my-bot/.env` | `1`（`2` 以上なら二重に追記している） |
| 値が空でないか | `grep -cE '^SLACK_BOT_TOKEN=.+' ~/apps/my-bot/.env` | `1`（`0` なら空） |
| どのキーが入っているか | `grep -oE '^[A-Z_]+=' ~/apps/my-bot/.env` | キー名の一覧 |

キー名だけを見る確認では、値が空のまま書き込まれていても気づけません。変数名の打ち間違いなどで空の値が入ることがあるので、2 つ目の確認も併せて行うと安心です。

**最終的な確認は、アプリを起動して認証が通るかどうか**で行います。

## 空の値が入ってしまったときの直し方

`read` と `printf` で変数名を打ち間違えると、`printf` は存在しない変数を空として扱い、エラーも出さずに `MONITOR_PING_URL=` のような空の行を書き込みます。`grep -cE '^KEY=.+'` が `0` を返したら、次の手順で入れ直します。死活監視サービスの ping URL をサーバー上の設定ファイルに入れ直す例です。

**1. 空の行だけを消す**

```bash
sed -i.bak '/^MONITOR_PING_URL=$/d' ~/.config/monitor/ping.env
```

`=$` で「`=` の直後で行が終わっている」行、つまり値が空の行だけを消します。値の入った行は消えません。

**2. 値を受け取り、書き込む前に空でないか確かめる**

```bash
read -rs PING_URL_INPUT
[ -n "$PING_URL_INPUT" ] && echo 入った || echo 空
```

`[ -n ... ]` は「変数が空でないか」だけを判定するので、値は表示されません。`入った` と出たら次へ進みます。`空` と出たら `read` からやり直します。

**3. 追記して変数を消す**

```bash
printf '\nMONITOR_PING_URL=%s\n' "$PING_URL_INPUT" >> ~/.config/monitor/ping.env
unset PING_URL_INPUT
```

**4. 値の形式まで確かめる**

```bash
grep -cE '^MONITOR_PING_URL=https://ping\.example\.com/[0-9a-f-]{36}$' ~/.config/monitor/ping.env
```

`1` と出れば成功です。URL やキーの形式が決まっている値なら、このように正規表現で「形が正しいか」まで確かめられます。表示されるのは件数だけなので、値そのものは出ません。空ではないものの、別の値を貼ってしまったというミスもここで見つかります。

最後に、手順 1 で作られた `ping.env.bak` を削除します。`.bak` には元のファイルがまるごと残っていて、ほかのキーの値も含まれるためです。

:::message
`sed -i`（`.bak` なし）は Linux の GNU sed の書き方で、macOS の sed ではエラーになります。`-i.bak` はどちらでも動きます。
:::

2 の「書き込む前に空でないか確かめる」は、入れ直しのときに限らず、手順 1〜3 の `read` の直後に毎回はさんでもよい確認です。

## つまずきポイント

### 画面が止まったように見える

`read -rs` のあとは何も表示されないのが正常です。貼り付けて Enter を押せば次に進みます。シェルやプロンプトの設定によっては、Enter のあとに改行されず、次のプロンプトが同じ行に続くこともあります。これも正常です。

### 同じキーを二重に追記した

`>>` は追記なので、同じ手順を 2 回実行するとキーが 2 行になります。どちらの値が使われるかは、読み込むライブラリ次第です。入れ直すときは、先に古い行を消してから追記します。

```bash
sed -i.bak '/^SLACK_BOT_TOKEN=/d' ~/apps/my-bot/.env
```

`-i.bak` は macOS と Linux のどちらでも動く書き方です。ただし `.env.bak` には古い値を含む元のファイルがまるごと残るので、追記と確認が済んだら削除します。

### 2 行目の先頭の `\n` は何か

既存の `.env` が改行で終わっていないと、追記した行が前の行にくっついてしまいます（`OTHER_KEY=abcSLACK_BOT_TOKEN=...`）。先頭の `\n` はその保険です。空行が 1 行増えるだけで害はありません。

### 前後の空白が消える

`read` は標準の設定で、入力の前後の空白を取り除きます。token ならむしろ好都合ですが、前後に空白を含むパスワードをそのまま入れたい場合は `IFS=` を付けます。

```bash
IFS= read -rs PASS_INPUT
```

### bash と zsh の違い

この記事の 4 行は bash と zsh のどちらでも同じように動きます。ただし、入力前にメッセージを出したくて `read -p "Token: "` と書くのは bash だけの書き方です。zsh では `-p` は別の意味になるので、zsh では変数名とメッセージを `?` でつないで `read -rs 'SLACK_TOKEN_INPUT?Token: '` と書きます。迷ったらメッセージなしの 4 行を使うのが確実です。

### `set -x` を有効にしていると値が出る

デバッグ用に `set -x`（実行するコマンドを表示する設定）を有効にしていると、2 行目の `printf` が**展開後の値付きで**表示されます。

```console
+ printf '\nSLACK_BOT_TOKEN=%s\n' xoxb-xxxxxxxx
```

シェルスクリプトにこの手順を組み込む場合も同じなので、秘密を扱う部分では `set -x` を外します。

### クリップボードに値が残る

token をコピーして貼り付けると、値はクリップボードに残ります。クリップボード履歴アプリを使っている場合は、履歴にも記録されます。作業が終わったら別の文字列をコピーして上書きし、履歴からも削除しておきます。

## AI エージェントのルールファイルに書いておく

ここまでの手順を知っていても、AI エージェントの側が「トークンを教えてください」と聞いてきたり、値を含むコマンドを自分で実行しようとしたりしては意味がありません。エージェントが毎回読み込むルールファイルに方針や案内の形を書いておきます。

筆者は Claude Code で、`~/.claude/rules/secret-injection.md`というルールファイルを作成し、CLAUDE.md にインポートさせています。

:::details secret-injection.md の全文を開く
````markdown:secret-injection.md
# シークレットの扱いと注入手順の案内

API キー・トークン・パスワードの扱いと、人間が手で注入する手順の案内。

## エージェントがしないこと

- 値をチャットに貼らせない・要求しない
- 秘密を含むコマンドを自分で実行しない・`! <command>` で実行させない。注入は人間が**別ターミナル**で行う（会話履歴は平文 JSONL で永続化される）
- 秘密を含むファイル（`.env`・`auth.json` 等）を `cat` / Read しない。確かめ方は「検証」節
- 環境変数を一覧表示しない（`env`・`printenv`・`set`）。存在確認は `[ -n "${KEY+x}" ] && echo set || echo unset`

## 基本形（ローカルの `.env` へ追記）

```bash
read -rs KEY_NAME_INPUT
[ -n "$KEY_NAME_INPUT" ] && echo 入った || echo 空
printf '\nKEY_NAME=%s\n' "$KEY_NAME_INPUT" >> ~/path/.env
unset KEY_NAME_INPUT
grep -cE '^KEY_NAME=.+' ~/path/.env
```

- `read` / `printf` はビルトインで `export` もしないので、値は履歴・`ps`・子プロセス・会話ログのどれにも載らない
- 入力用の変数名はキー名と分ける（`_INPUT`）。取り違えると空の値がエラーなしで書き込まれる。2 行目が `空` なら 1 行目からやり直す。最終行 `1` で成功
- 先頭の `\n` は、改行で終わっていない既存ファイルで前の行と連結するのを防ぐ保険
- 前後の空白まで保持するパスワードは `IFS= read -rs`。`set -x` 中は展開後の値が表示されるので実行しない

## 提示の作法（必須）

`read -rs` は無音なので、コマンドを並べるだけでは伝わらない（複数行を 1 ブロックで示すと、どこに値を貼るのか分からなくなる）。雛形はまとめて書いてあるが、提示時は必ずこの形に開く。

1. 1 行ずつ番号を振り、行ごとに別のコードブロックにする
2. 各行が何をするかを 1 文添える。`printf` の行は「そのまま貼って実行。`%s` に 1 行目の値が入る」
3. 無音のプロンプトを明示する ─ 「カーソルが止まって入力待ちになる。貼り付けて Enter。画面には何も出ないが入っている」
4. 貼り付け先を否定形で名指しする ─ 「値を貼るのは 1 行目の入力待ちのときだけ。コマンド文字列の中には書かない」（`KEY=` の直後に書き込むと誤解されやすいため）
5. なぜこの形かを 2行で言う（履歴・`ps`・会話ログに残らない）。理由が分かると人間が手順を崩さない

## 注入先別の雛形

**リモートの `.env`（SSH）** ─ `ssh host "echo KEY=$VAR >> .env"` にしない（展開後の値がローカルとリモートの `ps` に見える）。複数キーは `'\nA=%s\nB=%s\n' "$V1" "$V2"`。ログイン後に基本形をリモートで打ってもよい。

```bash
read -rs KEY_NAME_INPUT
printf '\nKEY_NAME=%s\n' "$KEY_NAME_INPUT" | ssh user@host 'cat >> ~/path/.env'
unset KEY_NAME_INPUT
```

**パスワードファイル（新規作成）** ─ `umask` は新規作成時しか効かない（既存ファイルは元の権限のまま）ので `chmod 600` を併用。`>` は上書き、`printf '%s'` は改行を付けない。

```bash
read -rs PASS_INPUT
printf '%s' "$PASS_INPUT" | ssh user@host 'umask 077; cat > ~/path/app.pass && chmod 600 ~/path/app.pass'
unset PASS_INPUT
```

**GitHub CLI** ─ `printf '%s' "$GH_TOKEN_INPUT" | gh auth login --with-token`（前後に `read -rs` / `unset`）

**Cloudflare Workers** ─ `wrangler secret put KEY_NAME` の対話入力のみ。**pipe 注入しない**

**systemd** ─ `EnvironmentFile=` で秘密ファイルを指す。unit に `Environment=KEY=値` を書かない（`systemctl show` で誰でも読める）。注入後は `sudo systemctl restart <unit>`（多くのデーモンは起動時に 1 回だけ env を読む）

**Bitwarden** ─ `read -rs` の代わりに `bw get password <item>` の出力を各パターンのパイプ元にする。変数に置いたら最後に `unset`

## 検証（値を見ずに確かめる）

- `grep -c '^KEY=' f` → `1`（2 以上は二重追記）/ `grep -cE '^KEY=.+' f` → `1`（0 は空）
- 形が決まった値は形式まで: `grep -cE '^KEY=https://ping\.example\.com/[0-9a-f-]{36}$' f`
- キー一覧: `grep -oE '^[A-Z_]+=' f`（`'^PREFIX_[A-Z_]+='` で絞れる）。JSON の認証ファイルは `jq 'del(.. | .access_token?)'` のようにトークン欄を落として読む
- 疎通は秘密を出さないコマンドで（`wrangler whoami`・`gh auth status`）。トークンが混ざりうる出力は `grep -vE '[A-Za-z0-9_-]{30,}'` を挟む

## 失敗したとき

空の値が入ったら `sed -i.bak '/^KEY=$/d' f`、既存キーの差し替えは `sed -i.bak '/^KEY=/d' f` で消してから基本形で追記し直す。`sed -i`（接尾辞なし）は GNU 専用で macOS では失敗する。`.bak` には元ファイルがまるごと（ほかの秘密も）残るので、確認後に削除する。

## 後始末

- 手順の最終行に `unset` を必ず入れる。貼り付けた値はクリップボードと履歴アプリに残るので、消すよう一言添える
- 秘密を扱ったセッションのあと、ログを走査する: `grep -rnoE '(gho_|ghp_|github_pat_|sk-ant-|sk-|xoxb-)[A-Za-z0-9_-]{20,}' <ログ dir>/`
- **rotation ≠ 無効化**。漏洩対応は新規発行ではなく、**旧鍵が 401 を返す実測**で完了とする
- 長期有効な鍵を注入したら期限台帳への登録を提案する（失効時の影響・更新手順を note に書く）。台帳の場所はプロジェクトの CLAUDE.md 等に書いておく
````

## まとめ

- シークレットは**標準入力で渡す**。`read -rs` で受け取り、組み込みコマンドの `printf` から書き込み先へ流し、最後に `unset` する
- 確認は `grep -c` や `grep -oE '^[A-Z_]+='` で、値を画面に出さずに行う
- AI エージェントには値を渡さず、実行もさせない。ルールファイルに方針と案内の形を書いておくと、エージェントのほうからこの手順を案内してくれるようになる
