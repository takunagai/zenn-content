## TL;DR

- 500+ の AIサービスカタログから、お気に入り・タグ・メモで自分専用の「デッキ」を組める Web アプリ [AI Deck](https://ai-deck.app) を個人開発して公開しました
- 工夫したところは、「共通カタログ × ユーザーごとのカスタマイズ」を、コピーを一切配らず**差分だけ保存する 4 層構造**で実装したことです
- スタックは React 19/Hono/Cloudflare D1。読み取り偏重のワークロードに寄せた設計判断

## 「あのAIツール、名前なんだっけ」

気になる新しい AIサービスは毎週出ます。気になったものやそのまとめ記事をブックマークに放り込んでいく。数ヶ月後に残るのは、存在の忘却か「あの動画生成AI、名前なんだっけ…」とモニタに向かって独り言を言う自分です。

原因ははっきりしていて、ブックマークは「集める」道具だからです。集めて日々使わないものは埋もれる。埋もれたものはただのノイズです。

欲しかったのは網羅的な一覧ではありませんでした。**カタログの維持は誰かがやってくれて、自分は「使うものを選んで、並べて、メモを書く」だけ**の場所。カードゲームで言えば、全カードのリストが欲しいのではなくて、自分の40枚のデッキが欲しい。この比喩に行き着いた瞬間、アプリの動詞が「集める」から「組む」に変わって、作るものが決まりました。

それで作ったのが「AI Deck」です。

![AI Deck のデッキ画面 ─ グループ分けと関連リンクのメモポップオーバー](/images/ai-deck-introduction/deck-home.png)

カタログは運営（私）が整備する。ユーザーはお気に入り・並べ替え・グループ分け・色分けでデッキを組み、説明文やメモを自分用に上書きする。カタログにないツールは自分だけの非公開サービスとして登録する。組んだデッキは URLを発行でき、SNSなどでシェアすることもできます。

## データの丸ごとコピーを配らずにカスタマイズさせる

このアプリの技術的な工夫は、ほぼ一点に集約されます。
「共通カタログがあり、ユーザーはそれを自分用にカスタマイズできる」をどうテーブル設計に落とすか。
素朴な案から順に潰していきます。

**案1: ユーザー登録時にカタログ全件をコピーする。**
一番簡単で、一番ダメな案です。ストレージが「ユーザー数 × サービス数」で膨らむのはまだ我慢できるとして、致命的なのは更新が届かないこと。カタログ側で説明文を直しても、リンク切れを修正しても、コピー済みのユーザーデータは古いままです。

**案2: マスターテーブル + ユーザー差分テーブルの 2 層。**
大半のアプリはこれで足ります。ただ AI Deck の場合、もうひとつ問題が残りました。カタログ自体を誰がどこで管理するのか。毎週増えるデータを DB直編集で回すと環境ごとに状態がずれていく。かといって全部をシード SQL に寄せると、1 件直すたびにマイグレーションファイルが増えます。

つまり、分けるべき軸は 2つ。「**誰のデータか**（運営/ユーザー）」と「**どこで管理するか**（Git/DB）」。この2軸を展開したら、層が4つになりました。

| 層 | 中身 | 管理場所 |
|----|------|---------|
| Layer 1 | システムデフォルトのカタログ | Git（シード SQL） |
| Layer 2 | 運営によるカタログの上書き・追加 | DB |
| Layer 3 | ユーザーごとの状態・情報上書き・タグ調整 | DB |
| Layer 4 | ユーザー独自の非公開サービス | DB |

肝は Layer 1 と 2 の分離です。カタログの正本は Git 管理で再現性を確保しつつ、日々の修正は DBに積んで機動力を出す。DB側に溜まった変更は、3〜6ヶ月ごとに Git側へ「昇格」させて取り込みます。

### 保存するのは差分だけ

上書き系のテーブルは全カラム NULLABLE で、**ユーザーが変更した項目だけ**が値を持ちます。読むときに SQL の COALESCE で「Layer 3 → 2 → 1」の順に最初の非 NULL 値を拾えば、その人用にマージされたカタログが出てくる。

この方式の副産物が「初期値に戻す」の実装です。上書き行を消すだけ。元の値は Layer 1/2 に残っているので、消えません。設計時の試算では、フルコピー方式で約 41.5万フィールド必要だったものが差分方式では 4,965フィールドで済みました。

タダではなくて、代償もあります。Layer 3 の service_id は 3つのテーブルのどれかを指すので、外部キー制約が張れません。service_type カラムで参照先を判別する規約運用です。

## ハマりどころ ─ ローカルは動くのに本番でコケる

Drizzle ORM の `db.insert(table).values([配列])`。ローカルの SQLite では何事もなく動きます。本番の Cloudflare D1 では 500エラーになることがあります。開発環境で再現せず、発覚したのは本番デプロイ後でした。

対処は、複数件の書き込みを 50 ステートメントずつ D1 の batch API に流す薄いヘルパーです。

```typescript:apps/api/src/db/batch.ts の使い方
import { insertMany } from "../db/batch";

// 50 件ずつチャンクして db.batch() で実行する
await insertMany(db, table, dataArray);

// ローカルでは動くが、本番 D1 では 500 になりうる書き方
// await db.insert(table).values(dataArray);
```

:::message alert
D1 の batch() は原子性を保証しません。チャンク途中で失敗すると実行済みの書き込みは残ります。
:::

「ローカルで通った」が何の保証にもならない環境がある、という教訓を得ました。

## 技術選定は「乗り換え条件」とセットで決める

Cloudflare D1 は SQLiteベースで、各データベースは単一スレッドでクエリを1つずつ処理します。そのため、同時に大量の書き込みが発生するワークロードは苦手です。

データベースは D1 でいくのか、とは考えました。ただ AI Deck のワークロードは読み取り偏重で、書き込みは小さな UPSERT が散発する程度。しかも 4層構造が書き込む量そのものを削っています。なので、ある程度の規模までは D1 の弱点は致命的にはならない。

「ずっと D1」とは決めずに、移行の引き金だけ数値で決めています。DBサイズが5GB超、書き込み 50writes/sec 超、同時アクティブ 1,000人超、レイテンシ 50ms 超の頻発。どれかを踏んだら PostgreSQL系への移行を検討します。

## カタログは人間専用にしない ─ 公開API と MCP サーバー

情報が溜まったカタログは、人間が眺める以外の使い道があるデータ資産です。
なので、読み取り専用の公開 REST API と MCP サーバー（`https://api.ai-deck.app/mcp`）を付けました。Claude Code や ChatGPT(Codex) などの AIエージェントに AI Deck MCPサーバーを登録すると、こういう会話が成立します。

![Claude Code から AI Deck MCP に「YouTube 動画の BGM が欲しい」と聞いたところ](/images/ai-deck-introduction/mcp-demo.png)

「YouTube用の BGM が欲しい」という自然文から、カタログを関連度順に引いて返してくる。自分のデッキの中身も取得できるので、エージェントが「あなたが普段使っているツールはこれですよね」を前提に動けます。ブックマークアプリを作っていたはずが、気づけば AIエージェントの道具箱の索引も作っていました。

ただ、MCP は後付けであり、AI Deck の各アイテムは情報量が少なめなのでユーザーが満足する結果を得られない時もあると思います。ここは改善の余地ありと認識しています。
