![Claude Code のレビュー系コマンド 4 つの使い分け](/images/claude-code-review-commands/eyecatch.png)

Claude Code には、差分を読んで指摘を返すコマンドが複数あります。組み込みの `/code-review` と `/simplify`、同梱プラグインの `/security-review`、openai-codex プラグインの `/codex:review` です。

どれも「コードを見てくれるコマンド」に見えるので、最初はどれを打てばいいのか分かりませんでした。そこで Claude Code 2.1.251 の本体と各プラグインの定義から、それぞれが実際に何を探して何を返すのかを読んで整理しました。

結論から書くと、目的で引けます。

- バグを見つけたい → `/code-review`
- 動きを変えずにコードを綺麗にしたい（重複・冗長・非効率）→ `/simplify`
- 脆弱性が心配 → `/security-review`
- Claude 自身の見落としが心配 → `/codex:review`

差分を読む点は同じでも、探すものと出口（報告で止まるか、修正まで当てるか）が違います。以下、1 つずつ見ていきます。

## 基準になる `/code-review`

まず基準として `/code-review` を押さえておきます。既定のレビュー対象は現在の差分で、内部では `git diff @{upstream}...HEAD` と `git diff HEAD` の両方を読むため、コミット済みと未コミットの変更がどちらも対象になります。引数で PR 番号・ブランチ・パスも渡せます。

探すのは実行時の正確性バグが主で、クリーンアップ（再利用・簡素化・効率・抽象度）と CLAUDE.md 規約違反が副次的に付いてきます。結果は構造化された一覧としてホストの UI に返り、既定では報告のみで、修正は `--fix` を付けたときだけ適用されます。

effort レベル（`low` / `medium` / `high` / `xhigh` / `max` / `ultra`）で探索の角度数・候補数・検証の有無・報告件数の上限が変わります。この内部構造は別記事に分けて書きました。

https://zenn.dev/takna/articles/claude-code-code-review-effort

## `/simplify` との違い

同じ差分を読みますが、探すものと出口が逆です。`/code-review` は「バグを見つけて報告する」、`/simplify` は「品質の粗を見つけてその場で直す」。`/simplify` のプロンプトには「正確性のバグは探すな、それは `/code-review` の仕事だ」と明記されています。

| | `/code-review` | `/simplify` |
|---|---|---|
| 探すもの | 実行時の正確性バグ（+ 副次的にクリーンアップ） | 再利用・簡素化・効率・抽象度の 4 観点のみ |
| effort レベル | あり（low〜max、ultra） | なし（一段階） |
| 探索の構造 | レベル依存で 8〜10 角度 + 検証パス | 4 エージェント並列固定、検証パスなし |
| 出口 | 報告のみ（`--fix` を付けたときだけ適用） | 既定で修正まで適用する |
| 振る舞いの変更 | しない | しない（挙動が変わる修正はスキップして報告） |

`/simplify` の 4 観点は、`/code-review` のクリーンアップ角度と同じ定義を共有しています。

- **再利用**: すでにある共通処理の再実装。共有・ユーティリティモジュールと変更箇所の隣接ファイルを grep し、呼ぶべき既存ヘルパー名まで挙げる
- **簡素化**: 冗長・導出可能な状態、微妙に変えたコピペ、深いネスト、残った死んだコード
- **効率**: 重複計算・反復 I/O、並列化できるのに直列な処理、起動やホットパスに足された同期処理。クロージャや環境をキャプチャした長命オブジェクト（囲みスコープ全体を延命させるメモリリーク）も対象
- **抽象度**: 変更が適切な深さで入っているか。共通基盤に特例を積む修正は「浅すぎる」サインとして扱い、機構自体の一般化を促す

つまり `/simplify` は、`/code-review` の指摘のうち後ろ半分だけを取り出し、報告で止めずに修正まで走らせたものです。逆に `/code-review --fix` はバグ修正まで含めて適用するので、両者は「対象が違う `--fix` 付きレビュー」と捉えると混乱しません。

`/simplify` も引数で対象を渡せます（`/simplify [<target>]`）。承認を挟まずに修正を当てるコマンドなので、実行前にコミット済みか `git stash` 済みかを確かめておくのが安全です。

## `/security-review` との違い

`/security-review` は同梱プラグインのコマンドで、現在のブランチの未マージ変更をセキュリティ観点だけで監査します。git リポジトリ内でのみ動きます。

| | `/code-review` | `/security-review` |
|---|---|---|
| 観点 | 実行時の正確性・保守性 | 脆弱性（注入・認証認可・機密漏洩・安全でない既定値など） |
| 出力 | 構造化された指摘一覧（UI がレンダリング） | Markdown レポート本文のみ |
| 件数方針 | effort に応じて再現率と精度を切り替える | HIGH / MEDIUM に絞り、確信度スコアを付けて誤検出を抑える |
| 修正の適用 | `--fix` で可能 | なし（報告のみ） |

`/code-review` の探索角度にも SQL インジェクションなどの言語別の落とし穴は含まれますが、認可の抜け・秘密情報の取り扱い・依存関係のリスクまでは体系的に見ません。外部に公開する変更では、両方を通しておくのが安全側です。

## `/codex:review` との違い

openai-codex プラグインのコマンドで、Codex CLI 内蔵のレビュアーに差分を読ませます。中身は Claude ではなく GPT-5 系の Codex モデルなので、位置づけは「別モデルによるセカンドオピニオン」です。Codex CLI（`npm install -g @openai/codex`）と `/codex:setup` が前提になります。

| | `/code-review` | `/codex:review` |
|---|---|---|
| レビューするモデル | Claude（このセッション内） | Codex CLI 内蔵レビュアー（別プロセス・別ベンダー） |
| 対象 | 差分 / PR 番号 / ブランチ / パス | 作業ツリー（未追跡ファイル込み）または `--base <ref>` のブランチ差分 |
| 粒度の調整 | effort レベル 5 段階 | なし（`--scope auto\|working-tree\|branch` のみ） |
| 観点の指定 | 対象引数で絞る | 不可。フォーカス文を渡すとエラーになり `/codex:adversarial-review` に誘導される |
| 出力 | 構造化された指摘一覧 | Codex の出力をそのまま逐語で返す（要約・加筆をしない規約） |
| 修正の適用 | `--fix` で可能 | なし（review-only がコマンドの中核制約） |
| 実行の待ち方 | セッション内で完了まで | `--wait` / `--background` を選択。指定しないと 1 回だけ聞かれ、1〜2 ファイル程度でなければバックグラウンドが推奨される |

バックグラウンド実行はジョブとして管理され、`/codex:status` で進捗を、`/codex:result` で結果を取り出せます。`/codex:setup --enable-review-gate` を有効にすると、Claude が応答を終えるたびに自動でレビューを走らせるゲートになります。

足す価値があるのは、同じモデルの見落としを潰したいときです。`/code-review high` を通したうえでバックグラウンドに投げておく、という重ね方が噛み合います。逆に「この観点で見て」という指定が要るなら `/codex:adversarial-review` を使います。

## 実際の並べ方

4 つを毎回全部通す必要はありません。変更の性質で足していくのが現実的です。

| 変更の性質 | 打つもの |
|---|---|
| 日常のコミット前 | `/code-review low` か `medium` |
| リファクタ直後、差分が汚い自覚がある | `/simplify` を先に当ててから `/code-review` |
| マージ前・レビュー依頼前 | `/code-review high` |
| 認証・課金・外部公開が絡む | `/code-review xhigh` + `/security-review` |
| 判断を間違えたくない大きな変更 | 上に加えて `/codex:review --background` |

`/simplify` を先に当てるのは、クリーンアップで差分が整理されたあとの方が、`/code-review` の角度がバグに集中できるためです。逆順にすると、直したそばから指摘が古くなります。

## まとめ

- `/code-review` はバグを探して報告する。修正まで当てるなら `--fix`
- `/simplify` は品質の粗だけを探して、既定で修正まで当てる。バグは探さない
- `/security-review` は脆弱性だけを見て、Markdown レポートで返す。修正はしない
- `/codex:review` は別ベンダーのモデルに読ませるセカンドオピニオン。review-only で、観点の指定はできない

どれも差分を読むところは同じなので、「何を探すか」と「修正まで当てるか」の 2 軸で覚えておくと選び間違えません。
