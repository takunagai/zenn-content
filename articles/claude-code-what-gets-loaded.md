Claude Code を使い込むほど設定ファイルが増えます。CLAUDE.md、rules、スキル、サブエージェント、MCP、フック。そのうち「これは実際にモデルに読まれているのか」が分からなくなります。

自分の環境で棚卸ししたので、その結果を整理します。検証は v2.1.239 / macOS です。

## セッション開始時に乗るもの

| 種類                                      | 実体                                                       | 乗り方                           |
| --------------------------------------- | -------------------------------------------------------- | ----------------------------- |
| ハーネス本体の指示                               | バイナリ内蔵                                                   | 常時                            |
| 環境ブロック（cwd・git status・直近コミット・OS・モデル・日付） | 動的生成                                                     | 常時                            |
| ユーザー CLAUDE.md                          | `~/.claude/CLAUDE.md`                                    | 常時・全文                         |
| プロジェクト CLAUDE.md                        | `<repo>/CLAUDE.md`                                       | 常時・全文                         |
| `@import` されたファイル                       | CLAUDE.md 内の `@path` 行                                   | 常時・全文                         |
| rules                                   | `~/.claude/rules/**/*.md`、`<repo>/.claude/rules/**/*.md` | 常時・全文（後述）                     |
| メモリ索引                                   | `~/.claude/projects/<パス>/memory/MEMORY.md`               | 常時・全文                         |
| 個別メモリ                                   | 同ディレクトリの `*.md`                                          | recall 時のみ                    |
| 組込みツール定義                                | バイナリ内蔵                                                   | 常時・フルスキーマ                     |
| deferred ツール                            | 同上                                                       | **名前だけ**。スキーマは `ToolSearch` 後 |
| MCP の instructions                      | 各サーバーが返す                                                 | 常時                            |
| スキル                                     | `~/.claude/skills/`、プラグイン、`<repo>/.claude/skills/`       | **description だけ**。本文は呼び出し時   |
| サブエージェント                                | `~/.claude/agents/*.md`                                  | **description と tools だけ**    |
| フックの出力                                  | `~/.claude/hooks/` 等                                     | stdout がそのまま                  |

ポイントは太字にした 3 つです。スキルとサブエージェントは**定義ファイルの本文ではなく description だけ**が乗ります。だから 100 本あっても本文 100 本分にはならない代わりに、description が悪いと呼ばれません。deferred ツールも同じで、名前だけ見えていてスキーマは必要になってから読み込まれます。

## セッション中に積み上がるもの

上の表は開始時に確定する分です。そこから会話が進むごとに増えていくのが以下です。長いセッションで効いてくるのはこちらです。

| 種類                                    | 増えるタイミング                                 |
| ------------------------------------- | ---------------------------------------- |
| 発話と応答                                 | 毎ターン                                     |
| ツール呼び出しと結果                            | 呼び出しごと。Bash の標準出力や Read したファイルの中身がそのまま乗る |
| `UserPromptSubmit` フックの出力             | 発話ごと                                     |
| `PreToolUse` フックの `additionalContext` | ツール呼び出しごと                                |
| system-reminder                       | メモリの recall、ファイル変更の検知など、ハーネス判断で随時        |
| deferred ツールのフルスキーマ                   | `ToolSearch` で解決したとき                     |
| スキルの本文（SKILL.md）                      | `Skill` を呼び出したとき                         |
| サブエージェントの返却                           | 完了時。サマリのみで raw は乗らない                     |
| Web・MCP の取得結果                         | 取得のたび                                    |
| 貼り付けた画像・テキスト                          | 貼るたび                                     |
| 圧縮後の要約                                | 上限に近づいたとき。それまでの会話と置き換わる                  |

量として大きいのはツール結果です。ファイルを 1 つ読むだけで数 KB、`grep` や `ls` の出力もそのまま乗ります。設定を数 KB 削る話より、探索を 1 回減らすほうが効く場面は珍しくありません。読み取りの多い調査をサブエージェントに投げて、返りを構造化サマリだけにする設計が有効なのはこのためです。

## コンパクションが走ると何が消えるか

会話が上限に近づくと、それまでのやり取りが要約に置き換わります（コンパクション）。ここで残るものと消えるものが非対称です。

**残る**: 先の「セッション開始時に乗るもの」は毎回組み立て直されるので、そのまま残ります。CLAUDE.md も rules もツール定義もスキル一覧も消えません。

**消える**: 積み上がってきた側です。ツール結果の生データ、読んだファイルの中身、コマンドの出力、会話の細部。これらは要約に圧縮され、原文は失われます。

つまりコンパクション後に手元に残るのは「要約に書かれた分だけ」です。要約に何が残るかは制御できません。長い調査の途中で走ると、確認したはずの実測値やファイルパスが曖昧になった状態で作業が続きます。

対策は単純で、**消えて困る事実はディスクに書く**ことです。決定事項、実測値、次にやること。ファイルに書いてあれば読み直せますが、会話にしかない情報は復元できません。

同じ理由で、要約や引き継ぎメモに書かれた「残りタスク一覧」は鵜呑みにせず、着手前に実際の状態から導出し直すほうが安全です。要約が作られた時点のスナップショットであって、現在の状態ではありません。

## 罠 1 ─ rules はディレクトリごと自動で乗る

`~/.claude/rules/` 配下の `.md` は、CLAUDE.md に `@import` を書かなくても**再帰的に全文ロードされます**。サブディレクトリも対象です。

自分は CLAUDE.md 側に「必要になったら `rules/on-demand/xxx.md` を読むこと」と書いて、読まれるまで乗らないつもりでいました。実際には最初から全部乗っていました。`@import` 行だけ見て判断すると外します。

確認方法はシンプルで、ファイル名で grep すれば分かります。

```bash
grep -rn '@' ~/.claude/CLAUDE.md   # @import は書かれているか
wc -c ~/.claude/rules/**/*.md      # 実際に乗っている総量
```

外したい場合は `settings.json` の `claudeMdExcludes` に絶対パスかグロブを書きます。

```json
{
  "claudeMdExcludes": [
    "/Users/you/.claude/rules/on-demand/**"
  ]
}
```

frontmatter に `paths:` を書けば条件付きロードにもできますが、発火するのは**そのパターンに一致するファイルを読んだとき**です。プロンプトの語やツール名では発火しません。

## 罠 2 ─「乗る」と「挙動を決める」は別

次のファイルはコンテキストには乗りません。それでも挙動を支配します。

- `~/.claude/settings.json` / `settings.local.json` ─ フック、権限、モデル、effort
- `<repo>/.claude/settings.json` / `settings.local.json`
- `~/.claude.json` ─ MCP 登録、プロジェクトごとの trust・allowedTools
- `~/.claude/commands/` ─ スラッシュコマンドの実体（名前だけスキル一覧に出る）
- `~/.claude/plugins/` ─ plugin.json、マーケットプレイス定義
- `~/.claude/keybindings.json`、`statusline-command.sh`

「モデルが読んでいないのに挙動が変わる」ものはここにあります。フックの設定を疑うときは、まずこの層を見ます。

## 減らすときに注意すること

肥大が気になって常時ロードを削る場合、支払う対価はトークンではなく**発火保証**です。

自動ロードは 100% 乗る機構です。一方「必要になったら読め」という指示はモデル判断でしか発火しません。公式ドキュメントもスキルの自動起動を "Claude uses skills when relevant" と書いていて、保証とは書いていません。

自分の環境で実際に外して試したところ、トリガー語を明示した依頼では 3 回中 3 回とも自発的に読みに行きました。ただしトリガー語が婉曲な場合や、会話が進んだ後に必要が生じる場合は別です。確実性が要るなら hook（`UserPromptSubmit` の stdout、`PreToolUse` の `hookSpecificOutput.additionalContext`）で機構として注入する必要があります。

そして節約額はプロンプトキャッシュ後の実効単価で見ます。キャッシュが効いていれば、フル単価で払うのはセッション開始時の 1 回だけで、以降のターンは 1/10 程度です。「毎ターン損している」ように見えて、実際の差は思ったより小さくなります。

結果として自分は、一度外した設定を元に戻しました。数 KB のために保証を手放し、それを買い戻すためにフックを新設するのは割に合わないと判断したためです。

外す判断がしやすいのは、次を満たすときです。

- 単体で大きい（全体の 2 割を超えるくらい）
- 発火トリガーが機械判定できる（プロンプト語・ツール名・ファイルパス）
- 発火し損ねたときの損害が小さい

小さいファイルを複数まとめて外すのが一番損です。節約は線形にしか増えませんが、外した本数だけ不発の機会が増えます。


### 条件付きで載せる手段

外すと決めた場合、条件付きで載せ直す機構は 4 つあります。トリガーにできるものがそれぞれ違います。

| 手段 | 条件にできるもの | 保証 |
|---|---|---|
| rules frontmatter の `paths:` | Claude が読んだファイルのパス | あり |
| `UserPromptSubmit` フック | プロンプトの中身（自分で判定する） | あり |
| `PreToolUse` フック | ツール名（Bash なら実行するコマンドも） | あり |
| スキル | 意味的な関連性 | なし（モデル判断） |

「プロンプトにこの語が出たらこのファイルを読ませたい」に直接応えるのは `UserPromptSubmit` フックだけです。CLAUDE.md や rules 側にキーワードトリガーのフィールドはありません。フックなら発話を受け取れるので、自分で grep して該当ファイルを `cat` すれば stdout がそのままコンテキストに入ります。

スキルも条件付きロードではありますが、発火はモデル判断です。確実に載せたいなら機構側に寄せます。

## まとめ

- CLAUDE.md と rules は全文が常時乗る。rules は `@import` 不要でディレクトリごと再帰的に乗る
- スキルとサブエージェントは description だけが乗る。本文は呼び出し時
- deferred ツールは名前だけ。スキーマは必要時
- settings.json 系はコンテキストに乗らないが挙動を決める
- 条件付きで載せたいとき、プロンプト内容を条件にできるのは `UserPromptSubmit` フックだけ
- コンパクションで消えるのは積み上がった側だけ。消えて困る事実はディスクに書く
- 常時ロードを外すのは保証を手放す取引。節約はキャッシュ後の単価で見積もる
