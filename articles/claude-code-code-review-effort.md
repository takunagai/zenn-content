![Claude Code の /code-review を実装から読む](/images/claude-code-code-review-effort/eyecatch.png)

Claude Code には `/code-review` というコードレビューのスキルが組み込まれています。差分を読んで、正確性のバグと、再利用・簡素化・効率まわりのクリーンアップを指摘してくれるものです。

ただ、ヘルプに出てくる説明は 1 行だけで、`low` と `max` で内部的に何が変わるのかまでは書かれていません。そこで Claude Code 2.1.251 の本体バイナリから、このスキルが実際に組み立てているプロンプトを読んで確かめました。この記事はその結果をまとめたものです。

先に結論を書くと、effort レベルは「考える時間の長さ」ではなく、**探索の角度数・候補数・検証の有無・報告件数の上限**をまるごと切り替えるスイッチでした。

## 何をするコマンドか

既定のレビュー対象は現在の差分です。内部では `git diff @{upstream}...HEAD` と `git diff HEAD` の両方を読むので、コミット済みの変更と未コミットの変更がどちらも対象になります。引数で PR 番号・ブランチ・パスを渡せば、そちらに切り替わります。

検出結果は `ReportFindings` という専用ツール経由でホストの UI に返り、重要度順の一覧としてレンダリングされます。各指摘は次の要素を持ちます。

- ファイル
- 行番号
- 要約
- 60 文字以内の短縮ラベル（UI の一覧表示用）
- 具体的な失敗シナリオ

検証パスが走った場合は、指摘ごとに `CONFIRMED` / `PLAUSIBLE` の判定が付きます。

## effort レベルで変わるもの

引数ヒントは次のとおりです。

```
/code-review [low|medium|high|xhigh|max|ultra] [--fix] [--comment] [<pr#>|<branch>|<path>]
```

レベルごとのパイプラインを表にすると、こうなります。

| レベル | パイプライン | 指摘の上限 | 志向 |
|---|---|---|---|
| low | 差分 1 パス、検証なし | 4 件（環境により 8 件） | 差分のハンクだけで判る明白なバグ |
| medium | 8 角度 × 各 6 候補 → 1 票検証 | 8 件 | 精度（メンテナが必ず直す指摘だけ） |
| high | 8 角度 × 各 6 候補 → 1 票検証（再現率寄り） | 10 件 | 再現率（取りこぼしより誤検出を許容） |
| xhigh / max | 10 角度 × 各 8 候補 → 1 票検証 → 掃討パス | 15 件 | 最大再現率 |
| ultra | クラウドのマルチエージェントレビュー（別系統） | ─ | 最深・課金対象 |

角度の内訳は、medium / high が「正確性 3 + クリーンアップ 3 + 抽象度 1 + 規約 1」、xhigh / max が「正確性 5 + クリーンアップ 3 + 抽象度 1 + 規約 1」です。正確性の角度には、ハンクの行単位走査、削除された行が守っていた不変条件が再確立されているかのチェック、呼び出し元をまたぐ影響の追跡などが含まれます。

プロンプトの文面自体も、レベルによって方針が書き分けられています。medium は「メンテナが実際に直す指摘だけを出せ」という精度重視、high 以上は「見逃すよりは出せ」という再現率重視です。xhigh / max では、検証で 1 票でも REFUTED でなければ通す、という指示まで入っています。

### low だけは性格が違う

low は他のレベルの縮小版ではなく、別物として設計されています。

- テスト・フィクスチャのハンク（`test/`、`*.test.*`、`fixtures/` など）をスキップする
- スタイル・命名・パフォーマンス・テスト不足を意図的に報告しない
- サブエージェントを使わず、全ファイルの読み込みもしない

見るのは、反転した条件、off-by-one、null 参照、消えたガード、falsy な 0 の判定、`await` 漏れ、変数の取り違え、catch での握り潰しといった実行時バグです。差分のハンクだけで判断できるものに絞る、という割り切りになっています。

なお、サブエージェントを起動できない環境では、どのレベルでも全角度をその場で 1 パス実行し、「ファンアウトなしの単発レビューだった」と明示して返す仕様になっています。

### レベルは記憶される

レベルを省略すると、前回タイプしたレベルが再利用されます。この値は設定に永続化されるので、一度 `/code-review high` と打つと、以降の `/code-review` は high で走ります。認識できない語を渡した場合は無視され、有効なレベル一覧が通知されます。

## オプション

### `--fix`

レビュー完了後、返ってきた指摘をそのままローカルの作業ツリーに適用します。適用後の再報告では、指摘ごとに `fixed` / `skipped` / `no_change_needed` の結果が付きます。

承認を挟まずにファイルを書き換えるので、実行前にコミット済みか `git stash` 済みかを確かめておくと安全です。

### `--comment`

対象が GitHub の PR のとき、指摘をインラインコメントとして PR に投稿します。ローカルの差分に対して使っても投稿先がないので、意味を持ちません。

紛らわしいのが `--post` で、これは `/code-review ultra` 専用のフラグです。完成したレビューを PR に「単一のコメント」として投稿します（GitHub のレビューとしてではありません）。`--comment` と併用した場合は `--post` 側が無視されます。

### `ultra`

コードをクラウドのサンドボックスに clone し、マルチエージェントで深くレビューする別系統の機能です。前提条件が多めです。

- git リポジトリ内であること（PR 番号を渡す場合はさらに GitHub リモートが必要）
- Claude.ai アカウントの認証。サードパーティプロバイダ経由では使えない
- 差分が大きすぎる PR、巨大なモノレポは弾かれる

引数がブランチとして解釈できない場合は「レビューへの注文メモ」として扱われますが、クラウド側のレビューはそのメモを読みません。返ってきた指摘をメモに沿って優先度付けするだけです。結果はタスク通知で届きます。

## 実行例

```
/code-review
```

現在の差分（コミット済み + 未コミット）を、前回使ったレベルでレビューします。

```
/code-review high src gas/src events scripts
```

effort レベル high で、指定したディレクトリ配下を対象にレビューします。パスは複数並べられます。以後、レベルを省略すると high が既定になります。

```
/code-review medium --fix
```

現在の差分を medium でレビューし、返ってきた指摘を作業ツリーに適用します。

```
/code-review max 128 --comment
```

PR #128 を最大 effort でレビューし、指摘を PR のインラインコメントとして投稿します。GitHub リモートが必要です。

```
/code-review xhigh feature/checkout-refactor
```

ブランチを対象に、掃討パス付きの高再現率レビューをかけます。リリース前の最終確認向けです。

```
/code-review ultra
```

現在のブランチをクラウドのマルチエージェントレビューに投げます。`/code-review ultra <PR番号>` で特定の PR も指定できます。

## 使い分けの目安

- 日常のコミット前 → `low` か `medium`。誤検出が少なく、読む手間が小さい
- レビュー依頼を出す前・マージ前 → `high`
- 不可逆な処理・課金・認証まわりを触ったとき → `xhigh` / `max`
- 大きなリファクタや外部公開の直前 → `ultra`

## 他のレビュー系コマンドとの違い

Claude Code には差分を読むコマンドが複数あります。目的で引くと、こうなります。

- バグを見つけたい → `/code-review`
- 動きを変えずにコードを綺麗にしたい（重複・冗長・非効率）→ `/simplify`
- 脆弱性が心配 → `/security-review`
- Claude 自身の見落としが心配 → `/codex:review`

## 読むときの注意点

実装を読んで、誤解しやすいと感じた点が 3 つありました。

**ローカルのレビューはセッション内で走ります。** ファンアウトする探索角度だけがサブエージェントで、司令塔は現在の会話にいます。したがって直前のやり取りの文脈は生きています。文脈から完全に切り離されるのは `ultra`（クラウドで clone し直すため）と、ホストが `ReportFindings` に対応していない環境で fork 実行になるときだけです。

**`--fix` は承認なしに作業ツリーを書き換えます。** 差分を確認できる状態で使うのが前提です。

**effort を上げるほど誤検出が混ざります。** high 以上は設計として「取りこぼすより出す」方針なので、`PLAUSIBLE` 判定の指摘が混ざることを前提に読む必要があります。件数の多さをそのまま品質の低さと受け取らないほうがいいと思います。

## まとめ

`/code-review` の effort レベルは、探索の角度数（8〜10）・角度あたりの候補数（6〜8）・検証パスの有無・報告件数の上限（4〜15）をまとめて切り替えるスイッチでした。low だけは別設計で、テストを見ず、スタイルも見ず、ハンクだけで判る実行時バグに絞ります。

普段は `medium`、マージ前は `high`、不可逆な変更を触ったときだけ `xhigh` 以上、という運用に落ち着きそうです。
