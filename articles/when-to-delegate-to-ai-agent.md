VPS に AI エージェントを常駐させて数か月運用しています。統括役ひとつと 21 の専門エージェント、4 部門。Telegram から話しかければ、調査も執筆も実装もチームが分担して進めます。

作った当初は「これで手が空く」と思っていました。実際には、投げないほうが速くて安い仕事が、想像よりずっと多い、というのが今の結論です。

この記事は、AI エージェントを自分で回している個人開発者・受託開発者に向けて書いています。常駐組織を持っていなくても判断基準はそのまま使えます。Claude Code のサブエージェントに投げるか自分でやるか、という日常的な選択にも同じ構造が働くからです。

## 結論: 委譲が得なのは 3 条件のどれかを満たすときだけ

- **並列** ─ 独立したトラックを同時に走らせたい
- **不在** ─ 自分が見ていない時間に進んでほしい
- **限界費用ゼロ** ─ 定額サブスクの枠に載るモデルで回せる

どれも満たさない仕事は、常駐チームがあっても手元の AI（Claude Code や Codex）で自分でやるほうが速く、安く、品質も安定します。

理由は単純で、委譲にはトークン代とは別に**固定費**がかかるからです。指示文を書く、打ち切り条件を決める、報告の様式を指定する、成果物を回収する、内容を検収する。この固定費が本体の作業量を超えた時点で、委譲は損になります。

## 投げる前の 6 問 ─ 2 段で判定する

手元のタスクをこの 6 問に通します。前半と後半で役割が違うので、判定の仕方も分かれます。

**前半: 何を買うのか（1 つでも Yes が必要）**

1. 並行して走らせたい独立トラックが 2 本以上あるか
2. 自分が見ていない時間に進んでほしいか
3. 使うモデルは定額サブスクの枠に載るか

**後半: 成立条件（すべて Yes が必要）**

4. 完成の判定を機械（テスト・型チェック・lint）でできるか
5. 指示文を書く手間は、本体の作業量より小さいか
6. 失敗に気づく仕組み（監視・完了報告）があるか

前半がすべて No なら投げません。前半に Yes があっても、後半に 1 つでも No があれば投げません。買うものが無いか、買っても回収できないかの、どちらかだからです。

:::message
ここまでが実務上の結論です。以降は「なぜこの 3 条件なのか」を、実際に外した例と効いた例で説明します。
:::

## なぜこの 3 条件なのか

### 並列 ─ ただし「並列に見えて実は依存」に注意

複数の独立した作業を同時に走らせられるのは、常駐チームの分かりやすい利点です。調査を 3 方向に分けて同時に投げれば、待ち時間は最も遅い 1 本分で済みます。

罠は、依存関係のある仕事を並列だと錯覚することです。実装 → レビュー → 修正 → 再検証のような連鎖は、カードを分けても直列にしか進みません。むしろカード間の受け渡しでオーバーヘッドが増えます。

判定は「片方の結果を見ないともう片方を始められないか」で行います。答えが Yes なら、それは並列ではありません。

### 不在 ─ 判断が挟まると価値が消える

自分が寝ている間、あるいは別の作業をしている間に進むこと。手元で対話的に回している限りは取れない価値です。ローカルでも定時実行に載せれば近いことはできますが、失敗したときに代わりに判断する層がない分、朝に止まっている確率が上がります。

ただし条件があります。途中で人間の判断を求めない設計になっていることです。結果を見て方針を決める必要がある仕事は、自分が起きるまで止まります。止まったまま朝を迎えるなら、寝る前に自分でやったほうが早い。

不在の価値を取りにいくなら、完成の定義を先に固めて、判断の分岐を作らないことです。

### 限界費用ゼロ ─ 統括役のモデルが効いてくる

エージェント組織のコストは、どの役に従量課金のモデルを置いたかで決まります。私の構成では、それが統括役です。

実装は GLM の Coding Plan（定額）、レビューは ChatGPT のサブスク枠で回していて、この 2 つは何回動かしても追加料金が出ません。一方、タスクを分解し、割り振り、進捗を追い、最後に統合する統括役には従量課金のモデルを当てています。統括役は思考量が多く往復も多いので、同じ 1 タスクでも課金が発生するのは統括役の分だけ、という構造になります。

ここを意識せずにチームを組むと、「サブスクで安く回っているはず」の実感と、実際の請求がずれます。委譲を判断する前に、どの役が従量でどの役が定額かを把握しておく必要があります。

## どれも満たさないときに残るのは固定費だけ

3 条件のどれも満たさないとき、委譲で買えるものはありません。残るのは固定費です。分解すると次のようになります。

- 指示文を書く（何を、どこまで、どの形式で）
- 打ち切り条件を決める（何往復で止めるか、詰まったら何を返すか）
- 報告様式を指定する（どこに、何を含めて）
- 成果物を回収する
- 検収する（意図どおりか確認する）

このうち検収は必ず自分の時間を使います。しかも**往復が必要な仕事ほど、固定費が繰り返し課金されます**。1 往復ごとに、指示を書き直し、待ち、また検収する。デザインや文章のように「見てから直す」性質の仕事が委譲に向かないのは、この構造のためです。6 問の 5 番目は、この繰り返し分まで含めて見積もってください、という意味です。

## 実際に外した例: 軽い UI 改善

手元に検証用の URL 短縮サービスがあります。その管理画面の見た目を整える作業を、チームの実力を測るテストとして投げてみました。視覚的な階層、余白のリズム、リンク 0 件のときの表示、フォーカスの見え方。軽い仕事です。

結果は次のとおりです。

- カード 6 枚（統括 → リード → 実装 → レビュー → 修正 → 統合）
- 所要 62 分
- 成果物はドラフトのプルリクエストまで到達（型チェックとテストは通過）

問題は中身でした。実際に変わったのは、狭い画面幅でテーブルの操作列が切れる不具合の修正で、頼んだ視覚的な階層や余白はほとんど手つかず。さらに、その修正で操作列の幅を固定したせいで、削除ボタンのラベルが 2 行に折り返される見た目の劣化が入っていました。

つまり、**デザインを良くするつもりが、見た目は悪くなった**わけです。私が手元で直したら 5 分でした。

なぜ外れたのか。指示が「視覚的な階層を整理」「余白のリズムを統一」といった抽象度だったからです。この種の指示に対して、モデルは**検証できる作業に読み替えます**。レイアウトが崩れないことは機械で確認できますが、美しさは確認できません。確認できるほうに寄っていくのは、ある意味で合理的な振る舞いです。

裏を返すと、委譲がうまくいく指示は「完成を機械で判定できる」形をしています。先ほどの 6 問の 4 番目は、ここから来ています。

## 実際に効いた例: X の日次発信

同じ日に、正反対の結果が出た仕事があります。X（旧 Twitter）への日次投稿の下書き生成です。

- カード 4 枚（統括 → リード → 素材収集 → 執筆 → 統合）
- 所要 17 分
- 成果物は、投稿予約シートに入った下書き 2 本と、その日の朝レビューノート

人間がやることは、朝にシートを開いて内容を確認し、承認のチェックを入れるだけです。チェックが入るまで投稿は物理的に発生しない仕組みにしてあるので、暴走の心配もありません。

これが効いたのは、3 条件のうち 2 つを満たしていたからです。不在（毎朝の定時実行なので、起きたときには終わっている）と、限界費用ゼロ寄りの構成（文面の生成を安価なモデルに寄せてある）。加えて、完成の定義が明確でした。何アカウント分を、何字以内で、どの列に、どの状態で入れるか。判断の分岐がありません。

## 手元の 3 系統をどう使い分けるか

現在の使い分けはこうなっています。

**ローカルの Claude Code**

対話的な実装、調査、その場の修正。会話の文脈をそのまま持っているので往復が最速で、委譲の固定費がゼロです。今日の削除ボタンの手直しのような「見て、直して、また見る」仕事は全部ここ。

**ローカルの Codex**

コードレビューと画像生成。別のモデルの視点が効く領域を担当させています。これも委譲ではありますが、固定費がほぼゼロなので 6 問には通しません。指示を書き直す往復が、そのまま会話の中で終わるからです。

**VPS の常駐チーム**

定型の日次運用、自分の不在時間に進めたい仕事、独立して並列にできる調査。要するに 3 条件を満たすときだけです。

順番としては、まず 6 問に通す。通らなければローカルの 2 系統でやる。この判断を挟むようになってから、無駄な委譲が目に見えて減りました。

## 組織を持つと維持コストがかかる

もうひとつ、作る前に知っておくべきことがあります。エージェント組織は、**沈黙する故障**を抱えます。

異常を検知したら Telegram に飛ぶ仕組みは作ってあります。定期的な死活確認、収集処理が空振りしたときの警告、正本と実機の設定差分。これらはちょくちょく届きますし、実際それで気づいて直したものも多い。監視は効いています。

それでも漏れるものがあります。同じ日に 2 件見つかりました。ひとつは、エージェントごとに持っていた認証情報が本体から分岐していて、2 体が期限切れで死んでいたこと。primary ではないモデルの認証だったので、フォールバックに吸われて通知が上がりませんでした。もうひとつは、GitHub のアクセストークンが有効期限より前に失効していて、コードを扱う部門のプルリクエスト作成が止まっていたこと。こちらも実際に投げるまで分かりませんでした。

共通点は、**フォールバックがあると故障が正常に見える**ことです。人間のチームなら「動けません」と言ってきますが、エージェントは代替経路で動き続けて、静かに劣化します。監視は「作れば安心」ではなく、漏れた分だけ後から足していくものになります。

つまり、通知が届く運用に育てること自体が維持コストです。しかも構成要素が増えるほど、監視すべき場所も増える。自動実行の経路が通っていることと、実際の仕事が流れていることも、別々に確認しないと分かりません。6 問の最後が「失敗に気づく仕組みがあるか」なのは、そのためです。

## まとめ

エージェント組織は労働力ではなく、**固定費資産**に近いものです。持っているだけで維持費がかかり、使えば固定費がかかる。だから「あるから使う」は最も損な使い方になります。

投げる前に、3 条件のどれを買っているのかを一言で言えるかどうか。

- 並列を買っているのか
- 不在を買っているのか
- 限界費用ゼロを買っているのか

言えないなら、それは手元でやったほうが速い仕事です。
